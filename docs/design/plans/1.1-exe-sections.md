# Plan: section-aware executable filtering, phase A (roadmap 1.1, no format change)

Repository: the repository root, crate `tsaur/crates/tsaur-core`. All line numbers refer to the tree as
read on 2026-09-25 (nothing was modified). "Measured" means run on this machine today; "README"
means the numbers quoted in `README.md` / `benchmarks/RESULTS-rust.md` (Windows reference machine);
"estimate" means an emulation or a guess and is labelled as such.

**Executive summary.** The `f` byte of a blob record only names a filter id and a 4-bit parameter,
and the v1 reader inverts the filter over the *whole* block from `ip = 0`
(`codec.rs:221-236`, `read.rs:417`). Therefore phase A cannot filter "parts of a block": the only
v1-compatible levers are (1) deciding *which blocks* get the filter from the file's section map
instead of the byte-sampling heuristics, (2) choosing the ARM64 alignment parameter exactly from the
section offset, and (3) placing block boundaries (at chunk granularity, chunking untouched) at the
transitions between code and non-code, so that blocks are pure code or pure data up to one chunk.
A calibrated emulation on the Linux equivalent of `corpus_binary` (15.6 MB of ELF, three files)
estimates the ratio gain of (1)+(3) at **about 0.2 points in block mode and ~0 in solid mode**;
the pack-time gain is ~3 of 17 filter trials avoided. The 1–3 point gap to 7-Zip on executables
is BCJ2's split streams plus the solid window, not the section boundaries; phase A is still
worth doing because it is cheap, removes the heuristic's misses (measured: two of seventeen
1 MiB blocks, 16 KB), makes the ARM64 parameter deterministic by construction, and builds the
section parser that phase B (format v2) needs anyway. Expectations in the README must say so.

A decision is needed before implementation (§3.8, "D1"): the writer freeze in spec §12 and
`CONTRIBUTING.md` says any change of output bytes for existing inputs needs a new generator
string, while `docs/V1-CONTRACT.md` §2 says the golden bytes may not change in 1.x. Phase A
changes output bytes for executable inputs only. The recommended way through is an **opt-in
option** (`pack --exe-sections`, `PackOptions::exe_sections = false`) in 1.1, flipped to default
together with the writer-generation bump that the other 1.1 item (sampling-based codec choice)
will force anyway.

## 1. The current mechanism (file:line, measured facts)

### 1.1 Filters (`tsaur/crates/tsaur-core/src/codec.rs`)

| what | where |
|---|---|
| filter ids `FILTER_NONE = 0`, `FILTER_X86 = 1`, `FILTER_ARM64 = 2` | `codec.rs:63-64`, `codec.rs:219` |
| `Encoded { codec, bytes, params, filter }` — the writer's per-block result | `codec.rs:53-61` |
| `x86_convert(data, ip, state, encoding)` — LZMA SDK `x86.c` E8/E9 converter, symmetric, `ip` and `state` supplied by the caller | `codec.rs:70-133` |
| `looks_like_x86(data)`: `len >= 4096`, not text, sample = first 256 KiB, hit = `E8/E9` followed 4 bytes later by `00`/`FF`; threshold `hits/len >= 0.1 %` | `codec.rs:138-145` |
| `arm64_convert(data, now_pos, encoding)` — XZ Utils `arm64.c` BL/ADRP converter on 4-byte words | `codec.rs:149-181` |
| `arm64_alignment(data)`: same size/text gate, tries the four word alignments on the first 256 KiB, needs `>= 0.5 %` near-BL words, returns the byte offset of the best alignment | `codec.rs:187-207` |
| `f` byte layout: `filter_id(f) = f & 0x0F`, `filter_param(f) = f >> 4` | `codec.rs:209-217` |
| `apply_filter(f, data, encoding)`: x86 with `ip = 0`, fresh `state = 0`; ARM64 from `off = min(param, 3)` with `now_pos = 0`; unknown id → `Error::Corrupt` | `codec.rs:221-236` |
| `compress_best(data, o)`: candidate list `[NONE]` + `X86` if `looks_like_x86`, else + `ARM64 \| off << 4` if `arm64_alignment`; for each candidate: filter → zstd (→ incompressible shortcut at 97 %) → xz (`>= 256 B`) → PPMd (text) ; smallest output wins, `STORE` if nothing shrinks | `codec.rs:337-383` |
| reader: `decompress_with(..., filter)` → `apply_filter(filter, out, false)` on the whole decoded block | `codec.rs:389-395` |

Consequences that bound phase A:
* The reader's inversion covers the whole block from offset 0 with `ip = 0`. The writer must use the
  same `ip` (it does: `apply_filter` is shared) — no "section-relative ip" is possible in v1.
* A partial-range filter (filter only bytes `[a, b)` of the block) would need the reader to know
  `a` and `b`; the `f` byte has no room for them and `BlobRecord.p` is defined as codec parameters
  (`manifest.rs:47-49`, spec §4.2). Any such scheme is a new filter id → phase B.
* The filter is kept only when the encoding is smaller (`codec.rs:353-357`), so a wrong decision can
  cost ratio and time, never correctness.

### 1.2 Block formation and the filter decision (`tsaur/crates/tsaur-core/src/pack.rs`)

| what | where |
|---|---|
| `PackOptions` (block_size default 1 MiB, codec `Best`, delta, …) | `pack.rs:29-95` |
| `Block { chunks: Vec<u32>, plain: Vec<u8>, delta: Option<Vec<u32>> }` — **no file, offset or kind information** | `pack.rs:122-128` |
| `Packer` state: current block, ready batch, `cur_delta`, recent window, … (no per-file context beyond `cur_delta`) | `pack.rs:215-266` |
| `ingest_chunk(&mut self, data)`: dedup by hash; block mode: `full` when `plain + data > block_size` or the delta dictionary rules say so; then append or open a new block | `pack.rs:402-485` (cut rule `pack.rs:441-457`) |
| `flush_ready`: blocks compressed in parallel with `codec::compress_best(&b.plain, &copts)`, then the delta trial; `BlobRecord { …, f: e.filter, … }` written; `codec_hist["filter:x86"/"filter:arm64"]` | `pack.rs:702-757` (call `pack.rs:725`, record `pack.rs:751`, histogram `pack.rs:744-749`) |
| `add_file`: delta candidates; whole-file path for containers / views / delta candidates (`chunk_buffer` → `chunk::boundaries` gives `(off, len)` per chunk, `pack.rs:931-937`); **streaming path** with `StreamCDC`, running `total` = file offset of the next chunk | `pack.rs:768-833` (streaming loop `pack.rs:817-825`) |
| `add_container`: ZIP/OPC members and PDF/JPEG segments chunked as parts (`parts[i]` in memory) | `pack.rs:837-893` |
| file-type detection today is by extension only (`container::is_zip_like`, `is_stream_container`) | `container.rs:38-41`, `container.rs:234-237` |

So the decision "filter or not" is taken inside `compress_best` from the block bytes alone; the
packer knows nothing about which file or file offset a block comes from, although both call sites
of `ingest_chunk` have that offset at hand (`total` at `pack.rs:822`, `off` at `pack.rs:933`).

### 1.3 Format and reader

* `format.rs` holds only framing (header, sections, trailer, CBOR helpers; `format.rs:21-38`); no filter field.
* `manifest.rs:39-58` `BlobRecord { off, clen, ulen, codec, n, p, f, d }`; `f` is skipped when zero (`manifest.rs:50-53`).
* `read.rs:397-437` `blob_plain`: decode with `b.f`, then verify every chunk hash — chunk identities are on unfiltered bytes (spec §4.2, line 111). The reader never reads `manifest.solid_block` (no usage in `read.rs`), so block grouping and block size are writer choices.
* Spec `docs/spec/TSAUR-FORMAT-SPEC-v1.0.md` §4.2 lines 111-119: filter table, "Writers try the applicable filter and keep the smaller …", and the explicit reservation "section-aware filtering driven by PE/ELF/Mach-O headers (filter only the code sections) and BCJ2-style split streams" for a later revision.
* `docs/V1-CONTRACT.md` §2 (lines 22-39): codec ids 0–5 and filter ids 1–2 frozen; unknown ids refused; golden archives frozen; §3 (lines 41-47) lists "section-aware executable filtering" as outside v1.0 (a writer feature added in 1.1 does not contradict that: the format does not change).
* Writer freeze: `lib.rs:46` `WRITER = "tsaur-core/1.0"` is written into every manifest (`pack.rs:984`), derived view (`pack.rs:912`, `canonical.rs:82,213`) and volume descriptor (`volumes.rs:369`); `tests/golden.rs:82-83,113-114,135-137,164-170` compare the writer's output with the committed archives.

## 3. Design of phase A

### 3.1 Principles

1. **No format change.** Only filter ids 1 and 2 with their existing parameters are written; block
   grouping is a writer choice (`manifest.solid_block` records the maximum, never read by readers).
   A 1.0 reader reads the output unchanged; `tsaur info` shows the same filter names.
2. **Bytes for non-executable inputs stay identical.** The new code path is entered only when a
   file (or container member) starts with an executable magic and parses; everything else runs the
   unchanged heuristic path. This is what keeps the golden archives byte-identical.
3. **The trial stays the arbiter.** Section information changes which filter is *tried* and where
   blocks are *cut*; the filtered encoding is still kept only when smaller. A hostile header can
   only cost ratio or time.
4. **Deterministic and hostile-input safe.** The section map is a pure function of the file bytes,
   the cut rule a pure function of the map and the chunk offsets; every parser read is bounds
   checked and every count capped; no panic, no allocation proportional to header-declared sizes.
5. **No new dependency** (see §3.9 for why).

### 3.2 Section map: new module `tsaur-core/src/exe.rs`

```rust
pub enum Arch { X86, Arm64 }                   // only architectures with a filter
pub struct CodeRange { pub start: u64, pub end: u64, pub arch: Arch }   // file offsets, end exclusive
pub struct CodeMap { pub ranges: Vec<CodeRange> }                        // sorted, coalesced, clipped
pub fn sniff(head: &[u8]) -> bool;             // magic test on the first 8 bytes, no allocation
pub fn parse(bytes: &[u8]) -> Option<CodeMap>; // whole buffer in memory (containers, tests)
pub fn parse_file(f: &mut std::fs::File, len: u64) -> Option<CodeMap>; // bounded reads for the streaming path
```

Reads: `head` = first 64 KiB; additional bounded reads only for ELF section tables (§3.3). All
integer reads are little-endian/big-endian explicit helpers over `bytes.get(a..b)?`; offsets and
sizes are `u64` with `checked_add`; a range is kept only if `start < end <= file_len`. Ranges are
sorted, coalesced when the gap is below 16 KiB (`.plt` + `.text` become one range; `.init`,
`.fini`, `.plt` alone are 27–1000 bytes) and dropped when shorter than 16 KiB after coalescing (no
block cut for a code island smaller than a chunk). `None` means "treat as an ordinary file".

### 3.3 Format parsers (hand-written, each ~60–120 lines)

**PE** (`MZ`; `e_lfanew` at `0x3C`, must be `>= 0x40`, `<= head.len() - 24`; `PE\0\0`): COFF header
`Machine` (`0x8664`/`0x14C` → X86, `0xAA64` → Arm64, `0x1C4` ARMNT/Thumb and others → `None`),
`NumberOfSections` (cap 96 per the PE specification), `SizeOfOptionalHeader`; section table at
`e_lfanew + 24 + SizeOfOptionalHeader`, 40-byte entries: `SizeOfRawData`, `PointerToRawData`,
`Characteristics`; code = `IMAGE_SCN_CNT_CODE (0x20) | IMAGE_SCN_MEM_EXECUTE (0x20000000)` with
`SizeOfRawData > 0`. Validated today against a real local PE (`distlib/w64.exe`: `.text` raw
`0x400..0xDC00` flagged `0x60000020`; `.rdata .data .pdata .rsrc .reloc` not code). A section
table beyond the 64 KiB head → `None` (real PEs keep it in the first pages).

**ELF** (`\x7fELF`, `EI_CLASS` 1/2, `EI_DATA` 1/2 — both endiannesses read explicitly, big-endian
ELF is parsed but its `e_machine` will not be X86/Arm64 in practice): `e_machine` `0x3E` x86-64 /
`0x03` i386 → X86, `0xB7` → Arm64, else `None`. Primary source (always at the front of the file):
program headers `PT_LOAD` with `PF_X` → `[p_offset, p_offset + p_filesz)` (`e_phnum` cap 2048,
table must lie inside `head`). Refinement when a section table exists: `e_shoff`/`e_shnum`/
`e_shentsize` with `e_shnum * e_shentsize <= 4 MiB` and inside the file → one `seek + read` in
`parse_file` (in `parse` it is a slice), sections with `SHF_EXECINSTR (0x4)` and `sh_type !=
SHT_NOBITS` → ranges; if any section-derived range falls outside an executable segment the section
table is distrusted and the segment ranges are used. Rationale for the refinement: with linkers
before `-z separate-code` the RX segment also holds `.rodata`/`.eh_frame` (30–40 % of the segment in
old binaries) which the filter should not see.

**Mach-O** (`0xFEEDFACF` 64-bit LE / `0xFEEDFACE` 32-bit LE; the byte-swapped `CF FA ED FE` /
`CE FA ED FE` files are big-endian and refused → `None`): `cputype` `0x01000007` → X86, `0x0100000C`
→ Arm64 (`0x07` i386 → X86); `ncmds` (cap 4096), `sizeofcmds` (cap 1 MiB, must be `<= head` or a
second bounded read); walk `LC_SEGMENT_64 (0x19)` / `LC_SEGMENT (0x01)`, `cmdsize` must be `>= 72/56`
and consistent with `nsects`; sections (80/68 bytes) with `flags & (S_ATTR_PURE_INSTRUCTIONS
0x80000000 | S_ATTR_SOME_INSTRUCTIONS 0x400)` and `offset != 0` → ranges; if the `__TEXT` segment
has no flagged section, fall back to the segment's `[fileoff, fileoff + filesize)` minus nothing
(coarse, still safe).

**Fat/universal** (`0xCAFEBABE` big-endian, `0xCAFEBABF` with 64-bit entries): `nfat_arch` cap 32
(this also rejects Java class files, whose bytes 4–7 are `minor, major >= 45`), each `fat_arch`
`{cputype, cpusubtype, offset, size, align}` (20 or 32 bytes) must lie inside the file and not
overlap the header; each slice is parsed as a thin Mach-O (depth 1, no nested fat) and its ranges
are shifted by `offset`; slices of other architectures contribute nothing. The map may hold X86
and Arm64 ranges at once (universal binaries).

**Everything else** (`#!`, WASM, `.class`, PE with unknown machine, archives `!<arch>`): `None`.

### 3.4 From the map to the block decision

New per-chunk value computed at ingest time:

```rust
enum Kind { Plain, Code { arch: Arch, align: u8 }, Data }   // Plain = not an executable file
```

* `Plain`: file has no map → heuristic path, byte-identical to today.
* `Code`: `>= 50 %` of the chunk's bytes lie in a code range of one architecture;
  `align = (4 - (chunk_start - range.start) % 4) % 4` for Arm64 (section file offsets are at least
  4-aligned in every format, so this equals `(-chunk_start) mod 4`), `0` for X86.
* `Data`: the rest of an executable file (headers, `.rodata`, `.rsrc`, `.reloc`, symbols, …).

Plumbing in `pack.rs`:

1. `Packer` gains `cur_map: Option<exe::CodeMap>` and `stream_off: u64` (like `cur_delta`,
   `pack.rs:237`). `add_file` (`pack.rs:768`) opens the file once, calls `exe::sniff` on the first
   8 bytes and `exe::parse_file` when `opts.exe_sections` is on; the whole-file path
   (`pack.rs:786-802`) uses `exe::parse(&data)`.
2. `ingest_chunk(&mut self, data: &[u8])` (`pack.rs:402`) becomes `ingest_chunk(data, kind: Kind)`;
   the two call sites pass the running offset (`total` at `pack.rs:822-823`; `off` from
   `chunk::boundaries` at `pack.rs:933-934`). The container path (`pack.rs:849-850, 869-870`) passes
   `Plain` in phase A1 and a per-member map in A4 (below).
3. `Block` (`pack.rs:123`) gains `kind: Kind` (the kind of its first chunk) and the cut rule at
   `pack.rs:441-457` gets a third clause: **cut when the incoming chunk's kind differs from the
   block's kind** (`Plain`↔`Code`↔`Data`, or another `arch`, or another `align`). Result: a block
   is entirely `Code` (with one alignment), entirely `Data`, or entirely `Plain`, up to nothing —
   the boundary lands on the chunk boundary nearest to the section boundary, the slop is inside the
   chunk that straddles it and is bounded by `chunk.max` (256 KiB, average 64 KiB). Starting an
   executable file also starts a new block (its header chunk is `Data`), so a code block never
   begins with the tail of another file. Blocks stay `<= block_size`; the delta rules are untouched.
4. `flush_ready` (`pack.rs:725`) calls `codec::compress_best(&b.plain, &copts, hint)` with
   `hint = FilterHint::Auto | None | X86 | Arm64 { align }` derived from `b.kind`.
5. `codec::compress_best` (`codec.rs:337-344`): the candidate list becomes
   `candidate_filters(data, hint)`: `Auto` → exactly today's code; `None` → `[FILTER_NONE]`;
   `X86` → `[NONE, X86]`; `Arm64 { align }` → `[NONE, ARM64 | align << 4]`. Nothing else in the
   function changes, so `Auto` output is byte-identical to today.
6. `PackReport` (`pack.rs:97-120`) gains `executables: usize` (files with a map) and
   `codec_hist` gains nothing new (the existing `filter:x86` / `filter:arm64` keys keep working;
   `tsaur info` — `ops.rs:322-330` — reports by id, unchanged).

Why alignment at chunk granularity keeps the chunking/dedup contract: chunk boundaries come from
`FastCDC` on the content (`chunk.rs:48-53`, `pack.rs:818`) and are never moved; chunk hashes, the
chunk table, the Merkle root and cross-archive dedup (`--ref`) are identical with and without the
option. Only `BlobRecord.n` grouping changes.

Optional **A4 (container members):** wheels, JARs/APKs and `.zip` bundles carry `.so`/`.dll`
inside; `add_container` has each member's bytes (`parts`), so `exe::parse(part)` per member gives
the same treatment for a few microseconds per member. Worth adding in the same PR only if the
corpus_arm64 files are packed as wheels in a measurement; otherwise a follow-up.

**A5 (not recommended for phase A, noted for the maintainer):** since the reader ignores
`solid_block`, the writer could use larger blocks for code only (e.g. 4 MiB) and recover part of
the 1.7-point solid-vs-block gap measured on corpus_binary. It changes the random-access promise
of the default profile and misdescribes `manifest.solid_block`; if wanted, it is a separate option
(`--code-block N`) with its own measurement, not part of this item.

### 3.5 Malformed and hostile headers

The packer parses untrusted input (anything the user points it at). Rules for `exe.rs`:

* every read through `get(..)` / `try_into` with `?` → `None`, never indexing; sizes and offsets
  `u64`, arithmetic `checked_*`; no `usize` casts of header values on 32-bit hosts before a bound check;
* counts capped before any loop (PE 96 sections, ELF 2048 program headers / 4 MiB section table,
  Mach-O 4096 commands / 1 MiB commands, fat 32 slices, recursion depth 1); the only allocation is
  the `Vec<CodeRange>` (≤ caps) and the bounded reads (64 KiB head, ≤ 4 MiB ELF section table);
* self-inconsistent headers (`cmdsize` too small, section outside its segment, `e_shentsize` not
  40/64, `PointerToRawData + SizeOfRawData` overflow or beyond the file) → the inconsistent part is
  dropped or the whole map is `None`; a lying header can only mislabel bytes as code or data,
  which the keep-if-smaller trial turns into a ratio/time cost, never a wrong archive;
* a parse never returns `Err`: there is no error path from the section map into `pack`, so
  `add_file` behaviour and error codes are unchanged for every input.

Unit tests (§4.2) enumerate truncations at every length and run a mutation campaign like
`tests/robustness.rs:265` (`manifest_and_chunk_index_decoding_never_panic`).

### 3.6 Determinism

* The map depends on file bytes only; explicit endianness; no floating point; no hash-map iteration
  order in the decision (ranges are a sorted `Vec`).
* The cut rule runs in `ingest_chunk`, sequentially, before blocks reach the parallel batch
  (`flush_ready`), so `--jobs` and batch boundaries do not influence grouping (the existing
  `parallel_packing_is_deterministic` test at `tsaur-cli/tests/cli.rs:307` keeps covering this).
* The ARM64 parameter is computed from the offset, not from a byte count of the sample, so it is
  identical for identical bytes by construction (it already was, but only through the heuristic).
* Cross-platform: nothing platform-dependent is read (no `mmap` differences, no path-dependent
  detection: magic only, not extension).

### 3.7 Why the output stays format v1

* Blob records use `f ∈ {0, 1, 2 | align << 4}` only — ids and parameter as registered in spec §4.2
  and frozen by `docs/V1-CONTRACT.md` §2.
* Grouping of unique chunks into blobs is unconstrained by the spec ("consecutive unique chunks
  grouped into blocks", §4.2 modes); the reader accepts any grouping (`read.rs:397-437`) and never
  reads `solid_block`.
* No new manifest key, no `requires` marker, no new section, no new codec or filter id: a 1.0.0
  reader reads a 1.1 archive with the option on exactly as it reads today's archives.
  `tools/compat_check.py` stays valid; a synthetic-executable archive produced with the option can
  be added to its inputs to make the claim executable (§4.2).

### 3.8 Golden archives and the writer freeze — decision D1

Facts: the golden inputs contain no executable (§1.4) → with the design above the golden
archives are reproduced byte for byte whether the option is on or off. But:

* spec §12 (line 296) and `CONTRIBUTING.md` "Format freeze" (lines 68-74) and rule 2 (lines 25-27):
  "the same inputs, options and build produce byte-identical archives in every 1.x release"; a
  change of those bytes "needs a new generator string, regenerated golden archives, a CHANGELOG
  entry and compatibility tests". A default-on phase A changes the bytes for executable inputs.
* `docs/V1-CONTRACT.md` §2 (lines 36-39): the golden archives may not change in v1.x — and the
  generator string is inside them (`pack.rs:984`), so a generator bump changes them.

Options:

| | what | freeze documents | golden archives |
|---|---|---|---|
| **(a) recommended for this PR** | `PackOptions::exe_sections: bool` (default `false`), CLI `pack --exe-sections`; `bench_rust.py` gets the rows "DEFAULT + --exe-sections" and "solid 32 + --exe-sections" | satisfied literally: existing inputs + existing options → same bytes | unchanged; no generator bump |
| (b) | default on, no generator bump, arguing the freeze is *checked* only by the goldens | breaks spec §12 as written for executable inputs | unchanged |
| (c) | default on, `WRITER = "tsaur-core/1.1"`, 1.0 goldens kept as reader fixtures, new 1.1 goldens (with an executable input) | needs an amendment of V1-CONTRACT §2 ("v1.x may not change them") by the maintainer | regenerated |

The other 1.1 item, "speed of `--codec best`" (codec chosen on a 64 KiB sample), inevitably changes
output bytes for the golden *text* inputs, so 1.1 cannot ship it without choosing (c) or an option.
Recommendation: implement phase A behind the option now, measure, and flip the default in the same

`make_golden.py`, `MANIFEST.sha256`, the CI determinism hash and `docs/V1-CONTRACT.md` §2 change.

## 5. Phase B (format v2): what it adds and why it needs a new filter id

Phase A leaves on the table exactly what the emulation and the README rows show: the difference
between BCJ (in-place E8/E9 rewrite) and 7-Zip's BCJ2, plus the solid window. Phase B, in the
single v2 bump the roadmap plans (`ROADMAP.md:44-49`):

1. **BCJ2-class split streams for x86.** The converter removes the 32-bit target of every `E8`
   CALL, `E9` JMP and `0F 80–8F` Jcc from the main stream and writes it big-endian into separate
   streams (calls, jumps), with a range-coded decision stream (7-Zip: adaptive bit models indexed
   by the previous byte) recording which opcodes were converted. Consecutive calls to the same
   function then become identical 4-byte tokens in a stream that LZMA models on its own, and the
   main stream loses the noisy operands. 7-Zip's gain of BCJ2 over BCJ on x86 executables is the
   1–3 points the README quotes; the emulation of §2.3 shows BCJ over none at 0.56 points on ELF,
   so BCJ2 is the larger lever by far.
2. **Why a new id.** Spec §4.2 defines a filter as a transform "applied before the codec and
   inverted after decoding" over one byte stream, identified by `f`'s low nibble with a 4-bit
   parameter. A BCJ2 blob is four streams (main, call, jump, decision), each with its own length
   and, optimally, its own codec (7-Zip uses LZMA for main/call/jump and its own range coder for
   the decisions). The reader must know the four lengths and the codec per stream *before*
   inverting anything; neither `f` nor `p` (codec parameters) can carry that with v1 semantics,
   and a v1 reader that met such a blob must refuse it rather than misread it — which is exactly
   what an unregistered filter id does today (`codec.rs:233`, `docs/V1-CONTRACT.md` §2: "unknown
   … filter ids … are refused, never skipped"). Hence a new filter id (or, cleaner in v2, a blob
   record with a `streams` array), registered in the v2 spec, golden archives for v2, and the
   `compat_check` across v1/v2 readers named in the roadmap.
3. **Section-aware phase B** (the second half of roadmap 2.0's line): with a v2 blob record the
   writer can also carry a per-blob **range list** (`[start, end)` pairs relative to the block)
   and a **section-relative origin** (`ip`) so that the converter runs only on the code bytes of a
   mixed block and consecutive blocks of one `.text` keep address continuity; the emulation says
   the origin alone is worth nothing at 1 MiB blocks, and the range list is worth the ~0.1 point
   that chunk-granular cuts already approximate, so both are cheap additions to the BCJ2 record
   rather than reasons for it.
4. **ARM64 and others.** The same split-stream idea applies to `BL` targets (XZ Utils and 7-Zip
   have no ARM64 BCJ2; 7-Zip 23+ gained an improved ARM64 filter with ADRP+ADD pairing, which is a
   candidate for filter id 3 in v2 — also in-place, so v1 could in principle register it, but the
   v1 id space is frozen by the contract). RISC-V and x86 Jcc conversion likewise.
5. **Code-only solid groups.** In v2 the writer may declare a separate block size for code blocks
   (the A5 note above) so that executables get 4–8 MiB windows while documents keep 1 MiB random
   access; the manifest would record both sizes. On corpus_binary this is worth up to the 1.7
   points between the default and `--solid 32` rows.

What phase A hands to phase B: the section parser (`exe.rs`), the `Kind` plumbing that attaches
file-position knowledge to chunks and blocks, the `FilterHint` seam in `compress_best`, and the
measurement rows that isolate the filter effect from the window effect.
