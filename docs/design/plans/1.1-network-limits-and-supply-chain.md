## Part A — network limits for `tsaur volumes serve` / `fetch`

### A.0 What exists today (verified)

**Admission (`tsaur/crates/tsaur-core/src/transfer.rs`).** `ServerLimits` (lines 105-128:
`max_connections` 64, `max_connections_per_peer` 8, `timeout` 30 s, `max_requests_per_second`
200, `min_rate` 64 KiB/s). `Gate` (143-192) holds `total: AtomicUsize`, `per_ip:
Mutex<HashMap<IpAddr, usize>>` and `buckets: Mutex<HashMap<IpAddr, Bucket>>`. `Gate::enter`
(155-180) refuses `Busy` when the total or the per-address count is reached (158-160), then runs a
per-address token bucket (rate `max_requests_per_second`, burst 2×, 161-176), forgetting full
buckets once more than 4096 addresses are tracked (166-169). `Gate::leave` (182-191) removes the

### A.1 Revocation file (`serve --revoke FILE`, `fetch --revoke FILE`) — proposal

**File format** (one fingerprint per line; the same parser as `--allow`):

```
# tsaur revocations — one certificate fingerprint per line
# (SHA-256 of the DER certificate, 64 hex characters; colons and letter case ignored;
#  '#' starts a comment; blank lines are ignored). A fingerprint in this file is refused
#  even when it is also given to --allow or --peer-id.
3f2a9c…64 hex…   # laptop key lost 2026-09-20
7B:1E:…:C4       # old server identity, replaced 2026-09-01
```

Parsing: read the file at start-up (never again during the run: restart to apply; state that in
`--help`), strip everything from `#`, trim, skip empty lines, `tls::parse_fingerprint` on the
rest. Errors: a bad line → `Error::Invalid("revocation file FILE, line N: fingerprint must be 64
hex characters")` (exit 7); a missing file → `Error::Missing("revocation file FILE: <io error>")`
(exit 5); an empty file is valid (zero revocations) and the start-up line says `revoked 0`.
Duplicates are harmless. Cap the file at 1 MiB (`Error::Limit`, exit 4) so a wrong path
(`--revoke big.tsr`) fails fast; the path is a local CLI argument, so the "network data never
selects a local path" invariant is untouched.

**Core API** (`tls.rs`): a `pub struct Revocations(HashSet<[u8; 32]>)` with `pub fn load(path:
&Path) -> Result<Revocations>`, `pub fn parse(text: &str, origin: &str) -> Result<Revocations>`
(unit-testable without a file), `contains`, `len`. Verifier changes:

* `PinnedClients` (tls.rs 115-147) gains `revoked: HashSet<[u8; 32]>`; `verify_client_cert`
  checks `revoked` **before** `allowed` and returns `rustls::Error::General("client certificate
  fingerprint … is revoked")`. The handshake then fails, and `Server::run` (transfer.rs 309-313)
  already closes the socket without a reply: the refusal is silent, nothing is read, nothing is
  sent after the alert. This is the "at the handshake" refusal.
* `PinnedServer` (79-113) gains `revoked` as well; `verify_server_cert` refuses even when the
  fingerprint equals `expected` ("peer certificate fingerprint … is revoked"). The client fails
  in `request` at `complete_io` (transfer.rs 563) before the request line is sent; nothing is
  written locally (the descriptor is only parsed after a successful reply).
* `server_config(identity, allowed)` and `client_config(identity, peer)` keep their signatures
  (they are called by tests at `transfer_limits.rs:54` and `transfer_tls.rs:57`); add
  `server_config_with(identity, &Pins)` and `client_config_with(identity, peer, &Revocations)`,
  where `pub struct Pins { pub allowed: Vec<[u8;32]>, pub per_set: …, pub revoked: Revocations }`
  (see A.4 for `per_set`). The old functions become wrappers with empty revocations.
* `ClientTls` (transfer.rs 598-602) gains `revoked: Revocations` (test literals at
  `transfer_limits.rs:193`, `transfer_tls.rs:82` need the new field; give `ClientTls` a
  `Default` so they can write `..Default::default()`).

**Before the handshake, too.** The requirement is "refused before/at the handshake even if listed
in --allow". Two cheap checks precede the handshake:

* `serve`: at start-up, intersect `--allow` (and every per-set list) with the revocations. A
  revoked fingerprint is *removed from the effective allow list* and reported: `note: 1 of 3
  allowed identities is revoked by FILE and will be refused`; in `--json` the `access` object
  gets `"revoked": 1`. The server still starts (an operator's shared revocation file must not
  take a script down); the verifier check remains as defence in depth. If the removal leaves the
  allow list empty, refuse to start with exit 3: `every --allow identity is revoked by FILE;
  nothing could connect` — starting a server nobody can use hides a mistake.
* `fetch`: if any `--peer-id` is in the revocation file, refuse the whole command before any
  socket is opened: `Error::Policy("peer identity <fp> (--from <addr>) is revoked by FILE; edit
  the command instead of skipping the peer")`, exit 3. Skipping the peer silently would make a
  typo in the wrong file look like an unreachable peer.

**Option interactions and error messages** (all before anything is bound or connected):

| Combination | Result |
|---|---|
| `serve --revoke` without `--tls-identity` | exit 7, `--revoke needs --tls-identity: revocations are certificate fingerprints, and plain connections carry none` |
| `serve --revoke` with `--allow-anyone` | exit 7, `--revoke needs --allow or --allow-set: with --allow-anyone clients present no certificate, so there is nothing to revoke against` (rustls `with_no_client_auth`, tls.rs 158, never sees a client certificate) |
| `fetch --revoke` without `--peer-id` | exit 7, `--revoke needs --peer-id: a plain connection has no server identity to revoke` |
| `--revoke` file contains the server's own fingerprint | start anyway, warn on stderr (`this server's own identity is listed in FILE`); clients decide what they pin |
| revoked fingerprint also in a per-set list (A.4) | removed from that list too; counted once in `revoked` |

**Start-up output.** `access:` line gains `, revoked K` after the allowed count; JSON `access`
gains `"revoked": K` and `"revocations_file": "<path>"`.

### A.2 Global bandwidth cap for `serve` — proposal

**Limit.** `ServerLimits::max_bandwidth: Option<u64>` (bytes per second across all connections;
`None` = unlimited, the default, so existing behaviour and the `..ServerLimits::default()`
literals in tests are unchanged). CLI: `--max-bandwidth-kib <KiB/s>` (name chosen not to collide
with `--min-rate-kib`, which is a *client* obligation, not a server rate). `0` is rejected
(`exit 7: --max-bandwidth-kib must be at least 1`). Printed in the start-up lines as `bandwidth
cap 512 KiB/s` and in JSON as `"limits": {"max_bandwidth_kib": 512}` (add the other four limits
to that object at the same time; today the JSON line has no limits).

**Where it hooks.** One global token bucket of *bytes* in `Gate` (`throttle:
Mutex<Bucket>`, tokens = bytes, refill = `max_bandwidth` per second, capacity = one second of
rate, starts full). The accounting point is `impl Write for Deadline` (transfer.rs 358-363):
every byte the server sends, in plain or TLS mode (`StreamOwned` writes through the same
`Deadline`), passes there, so `handle`, `send_ok` and `send_ok_from_file` do not change. The
write path becomes:

1. clamp the chunk: `n = min(buf.len(), max(4 KiB, rate / 8))` so that even a 1 MiB
   `send_ok_from_file` step is paid in slices and no connection waits more than ~125 ms for one
   grant (fairness among connections is arrival order; no per-connection weighting);
2. `let waited = gate.take_bytes(n)` — under the mutex, refill, and if `tokens < n` compute the
   shortfall's duration, release the mutex, sleep that long (outside the lock), then deduct;
3. `self.deadline += waited` — time the server itself spent throttling is credited to the
   connection's budget, so the cap can never trigger the `min_rate` cut-off (`Budget::allow`,
   371-379) against a client that is consuming as fast as the server sends. This is the only
   interaction with the existing time budget and it is exact by construction;
4. write the slice with the per-operation timeout as today.

Status lines (`OK n\n`, `ERR …`) are counted too; they are tiny.

**Interaction with the other limits.** The cap is shared by all connections: with 64 connections
and a 1 MiB/s cap each gets ~16 KiB/s, below the 64 KiB/s `min_rate` — harmless because of step
3, but document that the effective per-client rate is `cap / active connections`. The per-address
request rate is unchanged (it limits connections, not bytes). Client side needs nothing: the
client's 30 s read timeout (transfer.rs 553) is per `read` call and bytes keep arriving at least
every `4 KiB / cap` seconds, which stays under 30 s for any cap ≥ 1 KiB/s (the CLI minimum).

### A.3 Cap on distinct client addresses served concurrently — proposal

**Limit.** `ServerLimits::max_peers: usize` (distinct source addresses with at least one open
connection; default `64` = `max_connections`, i.e. no change in behaviour by default). CLI
`--max-peers N`, `.max(1)` like the others.

**Where it hooks.** `Gate::enter` (transfer.rs 155-160): after the total/per-address checks, `if
mine == 0 && per_ip.len() >= self.limits.max_peers { return Admit::Busy }`. `per_ip` already
drops an address at its last `leave` (185-188), so "concurrently" is exactly "present in
`per_ip`". The refusal is the existing `Busy`: `ERR 503 busy: too many connections` in plain
mode, silent close in TLS mode, and the client already retries it with the bounded back-off
(`Dial::request`, 638-640). No new error code, no new client behaviour.

**What it is not.** A source address is a resource-accounting key, not an identity: several
clients behind one NAT share one slot, one IPv6 host can use many addresses. The identity limit
is the allow list. The rate-bucket map (`buckets`, up to 4096 entries) is untouched: an address
that is refused by `max_peers` never reaches the bucket.

### A.4 Per-set `--allow` lists — proposal

**CLI.** `--allow <fp>` keeps its meaning (may read every served set). New, repeatable:
`--allow-set <set id>=<fp>`: `<fp>` may read only that set. `<set id>` is 64 hex characters or
a prefix of at least 16 (what `inspect`, `split` and `serve` print, `main.rs:392,423,569`); at
start-up each prefix must match exactly one served set, otherwise exit 7 (`--allow-set 3f2a…:
no served set has this id` / `matches 2 served sets, give more characters`). Ambiguity is
impossible at run time because the prefix is resolved to a full id before binding. For many
rules, `--allow-file FILE` with one rule per line:

```
# tsaur allow list: <fingerprint> [set id ...]; no set id = every set; '#' comments
3f2a…                       # may read everything
9c41…  1b7e0a2f3c4d5e6f      # only set 1b7e0a2f…
```

`--allow-file` and `--allow`/`--allow-set` may be combined (union). Requires `--tls-identity`
(exit 7 otherwise, same wording as today's `--allow needs --tls-identity`, main.rs 491-493) and
excludes `--allow-anyone` (494-496 already refuses `--allow` + `--allow-anyone`; extend the
condition).

**Where it hooks.** Two places, both after the existing checks:

1. *Handshake*: `PinnedClients.allowed` becomes the **union** of all lists (global ∪ every
   per-set list) minus revocations; an identity that appears in no list is refused at the
   handshake as today (silent close).
2. *Request*: after a successful handshake, `Server::run` reads the client certificate from
   `session.conn.peer_certificates()` (rustls `ServerConnection` exposes the verified chain; the
   first entry is the end-entity certificate) and passes `client: Option<[u8; 32]>` into
   `handle` (452). `handle` consults `acl.may_read(client, &set_id)`:
   * `SETS` (466-471) lists only the sets the client may read (an all-sets client sees everything,
     an anonymous client in `--allow-anyone` mode sees everything: there is no identity to
     restrict);
   * `DESCRIPTOR | HAVE | PIECE`: a set the client may not read is answered exactly like an
     unknown set, `ERR 404 unknown set` (474). The client therefore learns nothing about sets it
     is not allowed to see, and the wording is unchanged. A silent close was considered and
     rejected: `closed_early` (517-520) makes the client retry 16 times per request, so an
     authorization failure would look like a busy server and cost seconds per piece; `404`
     stops the fetch at once ("no peer supplied an acceptable descriptor (peer: 404 unknown
     set)"). The `access:` line and `--help` must say that a set-restricted client is answered
     `404` for the other sets.

`Acl` lives next to `Gate`: `struct Acl { anyone: bool, any_set: HashSet<[u8;32]>, per_set:
HashMap<[u8;32] /*set*/, HashSet<[u8;32]> /*fp*/> }` with `fn may_read(&self, client:
Option<&[u8;32]>, set: &[u8;32]) -> bool { self.anyone || client.is_some_and(|c|
self.any_set.contains(c) || self.per_set.get(set).is_some_and(|s| s.contains(c))) }`. Plain mode
and loopback-without-TLS set `anyone = true` (unchanged behaviour). `Server::bind_tls` gains an
`acl: Acl` parameter through a new `bind_with_pins` constructor; the existing `bind*` functions
stay as wrappers.

**Start-up output.** `clients: 3 allowed identities (1 restricted to specific sets), revoked 1`;
JSON `access.allowed_clients`, `access.restricted_clients`, `access.revoked`. Per set, the
listing line (569) gets ` readers: all | 2` so an operator can see the mapping without exposing
fingerprints.

### A.6 Tests — proposal (all clock-aware, all on loopback, same `lab()`/`serve()` helpers)

New file `tests/transfer_policy.rs` (revocation and per-set lists) and additions to
`tests/transfer_limits.rs` (bandwidth, distinct addresses); unit tests inside `transfer.rs` and
`tls.rs` for the parsers and the gate.

Revocation:
1. `revocation_file_parses_comments_blank_lines_and_colons` (unit, `tls::Revocations::parse`):
   comments, trailing comments, colons, upper case, CRLF; a bad line names its line number; an
   empty file is empty; a > 1 MiB text is `Error::Limit`.
2. `revoked_client_is_closed_at_the_handshake_even_when_allowed`: server allows A and B, revokes
   B; B's `fetch` fails with "no peer supplied an acceptable descriptor", `no_volumes_written`,
   the error string contains no `ERR` code (silent close); A still fetches and joins.
3. `revoked_server_is_refused_by_the_client_before_any_request`: client revokes the server's
   fingerprint while pinning it; error contains "is revoked"; `no_volumes_written`; `list_peer`
   with the same revocations fails the same way; the server's `Timing.requests` stays 0 (observe
   through a plain counter on the server side or by asserting the client's `requests == 0` in
   the report path — simplest: assert on the error and on the absence of files).
4. `revocation_wins_over_allow_at_startup` (CLI, `cli.rs`): `serve --tls-identity s --allow A
   --revoke f` where `f` lists A → exit 3, stderr `every --allow identity is revoked`;
   with `--allow A --allow B --revoke f(A)` → starts, stdout `access:` contains `revoked 1`;
   `serve --revoke f` without `--tls-identity` → exit 7; `fetch --peer-id S --revoke f(S)` →
   exit 3 before connecting (the test gives an unroutable `--from 127.0.0.1:1` and asserts the
   message names the file, which proves no connection was attempted).

Bandwidth (lower bounds only, so that a slow runner cannot fail them; upper bounds are loose):
5. `bandwidth_cap_bounds_the_transfer_rate`: cap 256 KiB/s, `Want::Needed` on the 2+1 lab
   (about 500 KB of pieces + descriptor). Assert `report.seconds_total >= (bytes_received −
   cap) / cap` (one bucket of burst is free), and `bytes_received` equals the sum of the wanted
   volumes' payloads; assert the uncapped fetch of the same lab is faster only if the capped one
   took more than 2 s (a fast runner may finish both in the noise otherwise — same guard style
   as `transfer_limits.rs:141-143`).
6. `throttled_clients_are_not_cut_off_by_the_time_budget`: `timeout` 1 s, `min_rate` 1 MiB/s,
   cap 64 KiB/s, one 256 KiB piece (`piece_size: Some(262144)`): without the deadline credit
   the budget of `max(1 s, 256 KiB / 1 MiB/s)` = 1 s would end after ~64 KiB; the fetch must
   complete and join. This is the regression test for step 3 of A.2.
7. `bandwidth_cap_is_shared_between_connections`: two fetches in two threads (two `out`
   directories) at cap 256 KiB/s; `sum(bytes) / max(elapsed) <= cap × 1.5 + one burst`.

Distinct addresses:
8. `gate_refuses_a_new_address_beyond_max_peers` (unit test in `transfer.rs`, `mod tests`):
   `max_peers = 2`, `enter(a) → Ok`, `enter(b) → Ok`, `enter(c) → Busy`, `enter(a) → Ok` (a is
   known), `leave(b)`, `enter(c) → Ok`. Clock-free, portable. An integration test with a second
   loopback source address (`127.0.0.2`) is *not* portable: `std` cannot bind a source address
   before `connect`, macOS does not alias `127.0.0.2` by default, and `socket2` is not a

### A.7 What the trust document must say — proposal

`docs/design/VOLUME-TRUST.md`:

* Replace lines 155-157 ("there is no revocation list because there is no authority") with:

  there is no authority: each side may pass `--revoke FILE`, a text file of fingerprints it
  refuses even when they are pinned or allowed. A revocation reaches the other side through

  revocation, and the file is read once at start-up.*
* New §6.3 "Revocation": file format; checked before the handshake (start-up intersection) and
  at the handshake (verifier); refusal is silent on the server and an explicit error on the

### A.8 Risks and open points

* **`peer_certificates()` after the handshake**: the per-set feature relies on rustls exposing the
  verified client certificate on `ServerConnection` (`peer_certificates()` in rustls 0.23). If it
  returns `None` for a client that presented no certificate in a mixed configuration, `may_read`
  treats it as anonymous, which is only permitted in `--allow-anyone` mode; in allow-list mode the
  handshake already required a certificate. Verify with a test that the fingerprint obtained
  post-handshake equals the client's `Identity::fingerprint`.
* **Throttle granularity on Windows**: `thread::sleep` has ~15 ms granularity there; the 4 KiB
  minimum slice keeps the achieved rate within a few percent of the cap. The tests use lower
  bounds only.
* **Silent 404 for unauthorised sets is a usability trade-off**: a misconfigured per-set list
  looks like "the peer does not have that set". The server's start-up listing (`readers:` per
  set) and the CLI note are the mitigation; a `--verbose` server log is out of scope.
* **Signature churn**: `ClientTls` and `bind_tls` are public; the wrappers keep the old entry
  points, but the struct literal for `ClientTls` in two tests changes (`..Default::default()`).
* **No hot reload of the revocation file**: documented; a `SIGHUP`/file-watch reload would add
  platform code and is not needed for the roadmap item.
* **Cap and `min_rate` in one command line**: a cap below `min_rate × connections` is valid; the
  credit in A.2 step 3 makes it safe, and `--help` should say the cap is shared.

### B.1 `cargo deny` + `cargo audit` job — proposal

One workflow, `.github/workflows/supply-chain.yml`, one Linux job, no compilation of the
workspace (both tools work from `Cargo.lock` and `cargo metadata`), so it costs about one to two
minutes of Linux time per run. `cargo deny check advisories` already reads the RustSec database,
so `cargo audit` is not strictly necessary; it is kept in the scheduled run for its tree output
and because the roadmap names both. Prebuilt binaries via `taiki-e/install-action` keep the job
under a minute; the fallback `cargo install --locked` costs 5–8 minutes (cargo-deny compiles gix
and reqwest — measured here: the from-source build took well over ten minutes on this
container).

```yaml
# .github/workflows/supply-chain.yml
name: supply-chain

on:
  pull_request:
    paths:
      - "tsaur/Cargo.lock"
      - "tsaur/Cargo.toml"
      - "tsaur/crates/*/Cargo.toml"
      - "deny.toml"
      - ".github/workflows/supply-chain.yml"
  push:
    branches: [main]
    paths:
      - "tsaur/Cargo.lock"
      - "tsaur/Cargo.toml"
      - "tsaur/crates/*/Cargo.toml"
      - "deny.toml"
      - ".github/workflows/supply-chain.yml"
  schedule:
    # weekly: the advisory database changes even when the lock does not (Mondays 06:17 UTC)
    - cron: "17 6 * * 1"
  workflow_dispatch:

permissions:
  contents: read

concurrency:
  group: supply-${{ github.event_name == 'push' && github.sha || github.ref }}
  cancel-in-progress: ${{ github.event_name == 'pull_request' }}

jobs:
  deny:
    name: cargo deny (advisories, licenses, bans, sources)
    runs-on: ubuntu-latest
    timeout-minutes: 10
    steps:
      - uses: actions/checkout@11d5960a326750d5838078e36cf38b85af677262 # v4
      - uses: dtolnay/rust-toolchain@6bed0761d98439e5a578e2877258200ad565ba87 # stable branch, 2026-09
        with:
          toolchain: stable
      # prebuilt binaries, seconds instead of minutes; pin to the commit SHA of the release tag
      # (look it up when adding: `gh api repos/taiki-e/install-action/git/ref/tags/<tag>`)
      - uses: taiki-e/install-action@<SHA of the tag> # vX.Y.Z
        with:
          tool: cargo-deny,cargo-audit
      - name: Advisory database cache
        uses: actions/cache@<SHA> # v4
        with:
          path: ~/.cargo/advisory-dbs
          key: advisory-db-${{ github.run_id }}
          restore-keys: advisory-db-
      - name: cargo deny (full build graph, LGPL exception for cabac)
        run: cargo deny --manifest-path tsaur/Cargo.toml --config deny.toml check
      - name: Which builds reach the copyleft component (documentation-truth check)
        run: |
          # Today `cabac` is reachable in BOTH graphs through preflate-rs (see the finding at the
          # top of the plan). This step fails until either the documents stop claiming that the
          # lite build has no LGPL code, or the dependency becomes optional; keep it, because it
          # is the check that would have caught the claim.
          set -e
          echo "full graph:"; cargo tree --manifest-path tsaur/Cargo.toml --locked -e normal -i cabac
          echo "lite graph (must be empty once the lite build is really LGPL-free):"
          if cargo tree --manifest-path tsaur/Cargo.toml --locked --no-default-features -e normal -i cabac 2>/dev/null; then
            echo "::error::cabac is reachable without the lepton feature; the 'no LGPL code' claim is false"; exit 1; fi
      - name: cargo audit (RustSec, tree output; scheduled and manual runs only)
        if: github.event_name != 'pull_request'
        # no `--deny warnings`: the three informational advisories of 2026-09-25 (B.5) are
        # transitive and not fixable here; vulnerabilities still fail the run
        run: cargo audit --file tsaur/Cargo.lock
```

Notes on the choices:

* **Triggers.** Path-filtered for pull requests and pushes (a docs change or a code change that
  does not touch the manifests cannot change the dependency graph), weekly on schedule, manual
  on demand. A scheduled failure e-mails the maintainer; nothing blocks.
* **Not a required check.** A path-filtered workflow that does not run leaves a required check
  "expected" forever and blocks merging (the ruleset README already describes this problem for
  docs-only PRs). Keep `main.json` as it is; the maintainer sees the check on the PRs where it
  runs. If it should become required, drop the `paths:` filter for `pull_request` (the job is
  cheap) and add `deny` to `required_status_checks`.
* **Token permissions.** `contents: read` at workflow level; the job needs nothing else.
* **Two graphs.** The default-feature graph is checked with the `cabac` exception (it passes
  today). The lite graph is examined with `cargo tree -i cabac`, which is cheaper and more direct
  than a second deny configuration and fails today (finding at the top). `cargo deny` also has a
  global `--no-default-features` flag (verified with 0.20.2: `cargo deny --no-default-features
  check licenses` passes with the same file, because the exception is by crate name, not by
  feature) — it cannot express "LGPL only behind feature X", which is why the tree check exists.
* **cargo audit without `--deny warnings`.** With cargo-deny 0.20.2, `unmaintained =
  "workspace"` hides the two transitive unmaintained advisories, and the tool has **no setting
  at all for "unsound" informational advisories** (a config with `unsound = "deny"` is rejected:
  `expected '["all", "workspace", "transitive", "none"]'`), so it never reported
  RUSTSEC-2026-0253 (`lru 0.7.8`). `cargo audit` does; that is the reason to keep it in the weekly
  run, as a report (exit 0 on warnings, non-zero on vulnerabilities). If the maintainer wants the
  three current warnings to fail the run, use `--deny unsound --deny unmaintained` with
  `.cargo/audit.toml` ignores carrying a reason.
* `cargo-deny` fetches the advisory database over git (`gix`); on GitHub runners that works
  without configuration. Cache it to avoid a fresh clone each week.
* The `taiki-e/install-action` and `actions/cache` SHAs cannot be looked up from this container
  (GitHub's API answers 403 through the proxy); they must be pinned when the workflow is added,
  in the style of the existing pins (`# tag` comment).

### B.3 SBOM and attestations for the release workflow — proposal

**SBOM.** `cargo-cyclonedx` (CycloneDX Rust plugin, Apache-2.0) produces a CycloneDX 1.5 JSON
from `cargo metadata` without compiling. Because the dependency set differs per target
(`windows-sys` only on Windows, `redox_syscall` only on Redox), generate one SBOM per released
package **from the Linux job** with `--target <triple>` — no per-OS install cost. Alternative:
`cargo-sbom` (SPDX 2.3 or CycloneDX; simpler flags, no `--target`); CycloneDX is preferred
because GitHub's `attest-sbom` and most scanners accept it directly. The exact flags depend on the
installed version (`cargo cyclonedx --help`); the ones below are those of the 0.5 line and must be
confirmed when the step is added.


The `draft-release` job then attaches `*.cdx.json` next to the zips (add `packages/*.cdx.json`
to the `files:` list at release.yml:79-81) and names them in the release body. An SBOM of the
lite package generated this way lists `cabac 0.15.0 (LGPL-3.0-or-later)` as a component, which
is how a downstream scanner would have surfaced the finding at the top of this plan; the release
body must not say "no LGPL code" next to an SBOM that names it.

**Provenance attestations.** GitHub artifact attestations (`actions/attest-build-provenance`)
sign a SLSA v1 provenance statement for each package with Sigstore, using the workflow's OIDC
identity; users verify with `gh attestation verify tsaur-<ver>-<platform>-lite.zip --repo
iulianbondari/t-saur`. On GitHub-hosted runners this yields SLSA Build Level 2 (Level 3 would
need the build to run in a reusable workflow, which is not worth it for a draft-release flow).
`actions/attest-sbom` binds each SBOM to its package the same way.

```yaml
permissions:
  contents: read          # workflow default: least privilege

jobs:
  lite-packages:
    permissions:
      contents: read
      id-token: write       # OIDC token: the Sigstore signing identity of this workflow run
      attestations: write   # store the attestation on the repository
    steps:
      # … existing build, test and package steps unchanged …
      - uses: actions/attest-build-provenance@<SHA> # vX
        with:
          subject-path: pkg/*.zip
      - uses: actions/upload-artifact@ea165f8d65b6e75b540449e92b4886f43607fa02 # v4
        with:
          name: package-${{ matrix.tag }}
          path: pkg/*.zip*

  draft-release:
    needs: [lite-packages, sbom]
    permissions:
      contents: write       # only this job creates the draft release
      id-token: write
      attestations: write
    steps:
      # … download packages and sbom artifacts …
      - uses: actions/attest-sbom@<SHA> # vX
        with:
          subject-path: packages/*.zip
          sbom-path: packages/tsaur_x86_64-unknown-linux-gnu.cdx.json   # one call per (package, sbom) pair
      - uses: softprops/action-gh-release@3bb12739c298aeb8a4eeaf626c5b8d85266b0e65 # v2
        with:
          files: |
            packages/*.zip
            packages/*.cdx.json
            packages/SHA256SUMS
```

What needs `id-token: write`: only the two attestation actions (they request an OIDC token from
GitHub to obtain a short-lived Sigstore certificate). It is granted per job, not at workflow
level, and the workflow runs only on tag pushes (never on pull-request code), so the token can
never be reached by untrusted code. `attestations: write` stores the result; `contents: write`
moves from the workflow level (release.yml:11-12) to the `draft-release` job only. Attestations
are keyed by artifact digest, so creating them before the release is published (draft) is fine.
`docs/DISTRIBUTION-POLICY.md` §3.5 and the release body should tell users to run
`gh attestation verify` in addition to the SHA-256 check; `SECURITY.md` "Hardening advice" gets
the same line.

**Reproducible package builds** (`ROADMAP.md:30` lists them with this item): `shutil.make_archive`
(release.yml:52, `tools/package.py`) records file mtimes and the runner's zip order, so two runs
differ. Fix later with `SOURCE_DATE_EPOCH`-normalised timestamps and sorted entries in the zip
writer; not required for the attestation, which covers whatever bytes were built.

### B.4 `cargo-fuzz` targets — proposal

**Layout.** `tsaur/fuzz/` as its own package (`cargo fuzz init` creates it with
`[workspace]` empty so it is not a member of the main workspace; add `exclude = ["fuzz"]` to
`tsaur/Cargo.toml` to be explicit), depending on `tsaur-core` by path with `default-features`
matching the CI build. Seeds live in `tsaur/fuzz/corpus/<target>/` and are copied from existing
fixtures at first run (not committed twice): `crates/tsaur-core/tests/golden/*.tsr` (six
archives, 1.7–18 KB), `tests/golden/volumes-2p0/`, `volumes-2p1/` (`.tsrv` files),
`benchmarks/corpus/*.docx|*.pdf` (four committed container files), and a descriptor/request-line
seed set generated by a tiny build script.

**Entry points that need no change** (all `pub` today):

| Target | Calls | Oracle beyond "no panic / no sanitizer report" | Seeds |
|---|---|---|---|
| `reader_open` | `Reader::from_bytes(data.to_vec(), None)` (read.rs:247), then `entries()`, `entry_bytes(i)` for the first 4 entries, `verify(None)` | a `Reader` that opens must return either `Ok` bytes whose BLAKE3 matches the entry hash or an `Err` — never bytes that do not verify (the SECURITY.md promise) | golden `.tsr` |
| `container_zip` | `container::explode(data)` (container.rs:64); when `Some((recipe, parts))`, `container::rebuild(&recipe, &parts)` (192) | **bit-exact**: `rebuild == data`, otherwise the invariant of CONTRIBUTING rule 3 is broken | `benchmarks/corpus/*.docx` |
| `container_streams` | `container::explode_streams(data, cfg!(feature = "lepton"))` (314) + `rebuild_streams` (418) | same bit-exact oracle; without the `lepton` feature JPEG inputs are `None` by design | `benchmarks/corpus/*.pdf`, a small JPEG from `tests/golden/inputs/` if present |
| `canonical_docx` | `canonical::docx_to_markdown("f.docx", data)` (canonical.rs:77) | output starts with the provenance header when `Ok` | the `.docx` seeds |
| `canonical_pdf` | `canonical::pdf_to_text("f.pdf", data)` (209) inside `catch_unwind` | `pdf-extract` panics are known and contained at pack time (SECURITY.md "Converters cannot take the process down"); count only aborts, OOM and timeouts | the `.pdf` seeds |
| `volume_descriptor` | `format::cbor_decode::<VolumeSet>(data)` then `validate()`, `volume_name(i)`, `volume_pieces(i)`, `payload_len(i)` for `i < total()` (volumes.rs:105-136) | `volume_name` never contains a path separator; `validate` ok ⇒ every accessor is in bounds | descriptors extracted from the golden volumes |
| `manifest_cbor` | `cbor_decode::<Manifest>`, `cbor_decode::<ChunkIndex>` (already a robustness test at robustness.rs:265) | none | manifest sections of the golden archives |
| `codec_decompress` | first byte selects codec/filter/params, rest is data: `codec::decompress_with(codec, data, ulen ≤ 1 MiB, dict, params, filter)` (codec.rs:389) | `ulen` bound keeps memory small; exercises zstd, liblzma, ppmd-rust (pure Rust) and the BCJ inverse filters | compressed blobs of the golden archives |
| `paths_normalize` | `paths::normalize(str)` (paths.rs:16), `safe_join` (62) | an `Ok` path is relative, has no `..`, no drive letter, no control characters, ≤ 256 components | a few hundred crafted strings |

**Entry points that need a small visibility change** (proposal: a `fuzzing` Cargo feature on
`tsaur-core` exposing `#[doc(hidden)] pub mod fuzz` with thin wrappers, so nothing internal
becomes public in normal builds):

| Target | Wrapper | Today |
|---|---|---|
| `transfer_request` | `fuzz::serve_one(request: &[u8], sets: &Served) -> Vec<u8>`: runs `handle` over an in-memory stream that implements `Read + Write + Budget` | `handle` (transfer.rs:452), `Budget` (371) and `read_line_bounded` (392) are private; the robustness test drives them over TCP (robustness.rs:311), which is 100× slower than in-process fuzzing |
| `transfer_reply` | `fuzz::parse_reply(bytes: &[u8], max_len) -> Result<Reply>` around `exchange` (570) with a cursor | private; oracle: an `OK` reply above `max_len` is refused before allocation (`Error::Limit`) |
| `volume_header` | `fuzz::volume_header(&[u8])`, `fuzz::volume_trailer(&[u8])` around `decode_header` (volumes.rs:177) and `decode_trailer` (209) | `pub(crate)` / private; cheap and worth it because `inspect` trusts these to reject foreign headers |

The fixture for `transfer_request` (a served set) is built once per process from
`tests/golden/volumes-2p1/` via `volumes::inspect` — the same code path `Server::bind_tls` uses
(transfer.rs:223-231).

**Workflow.** `.github/workflows/fuzz.yml`: `workflow_dispatch` with inputs `target` (default
`all`) and `seconds` (default 120), plus a weekly `schedule` (a different day from the
supply-chain run). Nightly toolchain (`dtolnay/rust-toolchain` with `toolchain: nightly`),
`cargo-fuzz` via `taiki-e/install-action` (prebuilt) or `cargo install cargo-fuzz --locked`
(~1 min), `Swatinem/rust-cache` keyed on the fuzz manifest, then per target `cargo fuzz run
<target> -- -max_total_time=${seconds} -max_len=262144 -rss_limit_mb=2048 -timeout=20`;
`timeout-minutes: 45`; on failure `actions/upload-artifact` of `tsaur/fuzz/artifacts/` (the
crashing inputs) with `if: failure()`. Never in the ruleset, never on `pull_request`. Expected
weekly cost: sanitizer builds of the reader pull zstd, liblzma and (with the default feature)
lepton — roughly 6–10 minutes of build plus `targets × seconds`; with nine targets at 120 s that
is ~30 minutes of Linux time a week. Findings are handled like the robustness campaign's
(`robustness.rs:99-103` saves inputs under `target/robustness-findings/`): a crashing input is
minimised (`cargo fuzz tmin`), added to `tests/robustness.rs` as a regression seed, and fixed
on stable.

### B.6 Risks and open points

* **The "no LGPL code" claim** (finding at the top) is the one item here that affects users
  today: fourteen statements, the release body and the package README. Whatever option the
  maintainer picks, the supply-chain job's tree check should stay red until the documents and
  the lock agree.
* **Three RustSec informational advisories** (RUSTSEC-2024-0384 `instant`, RUSTSEC-2026-0192
  `ttf-parser`, RUSTSEC-2026-0253 `lru`, all transitive via `reed-solomon-erasure 6.0.0` and
  `pdf-extract 0.12`) are not enforced by the proposed configuration; they are reported by the
  weekly `cargo audit`. Upgrading or replacing those two direct dependencies is the only fix.
* **Action SHAs**: `taiki-e/install-action`, `actions/cache`, `actions/attest-build-provenance`,
  `actions/attest-sbom` must be pinned to commit SHAs when added; this container cannot query
  GitHub's API (403 through the proxy), so the YAML above carries placeholders on purpose.
* **cargo-deny schema drift**: the `[advisories]`/`[licenses]` `version = 2` keys and
  `unmaintained = "workspace"` are the 0.16+ schema; the run in B.5 shows which keys the
  installed version accepted. Pin the tool version in the workflow (`tool: cargo-deny@X.Y.Z`)
  so a schema change cannot break a release week.
* **Advisory noise on the weekly run**: an "unmaintained" advisory for a transitive crate (e.g.
  `instant`, `lru 0.7`, both pulled by `pdf-extract`) fails `cargo audit --deny warnings`; the
  `ignore` list with a reason is the escape hatch, and `unmaintained = "workspace"` keeps cargo
  deny quiet about transitive ones.
* **SBOM per target from Linux**: `cargo cyclonedx --target` needs the target's `std` installed
  (`targets:` in the toolchain step) even though nothing is compiled; if a future version
  compiles build scripts, generate the SBOM in each matrix job instead (small extra cost).
* **Fuzz builds with `lepton` on nightly**: `lepton_jpeg`/`cabac` compile fine on nightly, but a
  sanitizer build doubles the compile time; start with `--no-default-features` for every target
  except `container_streams`, which needs the feature to reach the JPEG path.
* **Duplicates policy**: `multiple-versions = "warn"` never fails; if the maintainer wants a
  ratchet, list today's 17 names under `[bans].skip` with the older version and switch to
  `"deny"` so that a *new* duplicate fails while the known ones are tolerated.
* **Minutes**: PR cost ≈ 1 Linux minute only when manifests change; weekly ≈ 2 (supply) + ~30
  (fuzz) Linux minutes; release adds ≈ 2 minutes (SBOM job) + seconds per attestation. macOS
  minutes are not involved in any new job.
