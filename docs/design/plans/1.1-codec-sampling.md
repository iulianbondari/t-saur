## 1. The current algorithm and where the time goes

### 1.1 Code path (file:line references are against the current tree)

**Block formation — `tsaur/crates/tsaur-core/src/pack.rs`**

* `PackOptions` (pack.rs:30–67), defaults (pack.rs:69–95): `block_size: 1 << 20`, `level: 19`,
  `codec: CodecChoice::Best`, `batch: 0` (= CPU threads), `delta: true`.
* `Packer::ingest_chunk` (pack.rs:402–485): unique chunks are appended to `current: Block`; a
  block is closed when the next chunk would exceed `block_size` (pack.rs:446) or when the delta
  dictionary changes (pack.rs:447); closed blocks go to `ready`, and `flush_ready` runs when
  `batch_ready()` (pack.rs:397–399: `ready.len() >= batch_size()` or 128 MiB in flight;
  `batch_size()` pack.rs:385–391 = `--jobs` or `rayon::current_num_threads()`).
* `Packer::flush_ready` (pack.rs:702–757): `blocks.par_iter().zip(dicts)` (pack.rs:721–734) calls
  **`codec::compress_best(&b.plain, &copts)`** (pack.rs:725) per block with
  `CodecOptions { level, long_window_log: 27, dict, choice }` (pack.rs:707); when the block has a
  delta dictionary it *additionally* runs `zstd_compress_with_prefix` at level 19 (pack.rs:726–731)
  and keeps the smaller; the result is written in block order (pack.rs:735–755) and the codec id,
  parameters and filter are recorded per blob in `BlobRecord { codec, p, f, d }` (pack.rs:751,
  `manifest.rs:39–58`).

**Codec trial — `tsaur/crates/tsaur-core/src/codec.rs`**

`compress_best` (codec.rs:337–383), for one block `data`:

1. `best = STORE` (codec.rs:338).
2. Filter candidates: `[FILTER_NONE]`, plus `FILTER_X86` if `looks_like_x86(data)` (codec.rs:138–145,
   first 256 KiB, ≥ 0.1 % `E8/E9 … 00|FF` hits) or `FILTER_ARM64 | off<<4` if `arm64_alignment`
   (codec.rs:187–207) (codec.rs:339–344).
3. For each filter (codec.rs:345–381): `input` = filtered copy (codec.rs:221–236);
   `consider(codec, out, params)` keeps `out` only if **strictly smaller** than the current best
   (codec.rs:353–357) — the tie-break is therefore *first tried wins*: unfiltered before filtered,
   and within a filter zstd, zstd+dict, xz, PPMd.
4. `try_zstd` / `try_xz` for `Best`; `try_ppmd` for `Best` only when `looks_like_text(input)`
   (codec.rs:258–267: **first 64 KiB** of the block, no `0x00`, ≥ 97 % text-ish bytes) (codec.rs:358–360).
5. zstd -19 first (`zstd_compress`, codec.rs:284–294, window = ceil(log2(len)) capped at 27);
   `incompressible = z.len() * 100 >= input.len() * 97` (codec.rs:364); with `o.dict` also
   zstd+dict (granular mode) (codec.rs:366–369).
6. If incompressible and `Best`: `continue` to the next filter (codec.rs:371–373) — xz/PPMd skipped.
7. xz preset 9e with a block-sized LZMA2 dictionary (`xz_compress`, codec.rs:299–311) if len ≥ 256
   (codec.rs:374–376); PPMd order 16, memory `clamp(16·len, 16 MiB, 256 MiB)` (`ppmd_params`
   codec.rs:240–243, `ppmd_compress` 245–249) if len ≥ 1024 (codec.rs:377–380).
8. Return the smallest `Encoded { codec, bytes, params, filter }` (codec.rs:382).

So on a 1 MiB text block `best` runs zstd -19 + xz 9e + PPMd; on a machine-code block it runs
zstd -19 ×2 and xz 9e ×2 (both filter variants); on an incompressible block zstd -19 only (×2 if
it looks like code).

**CLI — `tsaur/crates/tsaur-cli/src/main.rs`**: `--level` (main.rs:87–88, default 19), `--codec`
(main.rs:89–92, default `best`, parsed by `CodecChoice::by_name` main.rs:767), `--jobs`

**Benchmark — `benchmarks/bench_rust.py`**: `pack()` (bench_rust.py:94–103) times the whole

## 2. Proposed design

### 2.1 Sampling strategy (which bytes, how many)

**The roadmap's "64 KiB sample" must not be the block prefix.** [measured] A 64 KiB prefix
predicts the wrong codec on 2/4 blocks of `corpus` and 3/7 of `corpus_versions`, costing **+8.68
and +6.41 points** of ratio (blocks are concatenations of chunks from several files; the first
64 KiB is one file's most compressible stream, e.g. corpus block 0: prefix says PPMd 6,403 B vs xz
7,968 B, the full 1 MiB block is xz 749,372 vs PPMd 881,553). A 128 KiB prefix is still wrong on
1/4 and 2/7.

**Proposed sample: `n` evenly spaced slices of 8 KiB, offsets rounded down to a multiple of 4.**

```text
SLICE = 8 KiB
n(len) = clamp(len / 128 KiB, 8, 32)            // 1 MiB block -> 8 slices = 64 KiB; >= 4 MiB -> 32 slices = 256 KiB
off_i  = (i * (len - SLICE) / (n - 1)) & !3      // i = 0..n-1; first slice at 0, last ends at len; 4-byte aligned
full trial instead of sampling when len <= 2 * n * SLICE   // <= 128 KiB for the default block size
```

Why these values:

* 8 × 8 KiB at 1 MiB ("S8x8") is the best measured configuration: **0 / 1 / 0 wrong blocks, loss
  0.00 / +0.37 / 0.00 points** on corpus / corpus_versions / corpus_elf, codec time **1.21× /
  0.96× / 1.41× zstd -19** (vs 2.9× / 3.0× / 2.3× today) [measured, winner-only scheme, §2.2].
  4 × 16 KiB is equivalent at 1 MiB but wrong on the 3.6 MiB `--solid 4` text block (+4.33 pt),
  where 8 × 8 KiB, 8 × 16 KiB and 16 × 4 KiB are all right [measured, `blocks_solid.jsonl`]:
  more slices matter more than more bytes. Scaling `n` with the block (up to 32 slices = 256 KiB
  at ≥ 4 MiB) is an **[estimate]** interpolated from those points; it keeps the sample ≤ 6 % of
  the block and must be verified on `--solid 4/8` in the PR (§3.4).
* The full-trial threshold `2·n·SLICE` (128 KiB at the default) is where sampling stops paying:
  a sampled block costs ≈ 3·sample + 1·block, a full trial ≈ 3·block; they cross at block = 1.5·sample.
  It also means the **golden archives are never sampled** (§2.5).
* 4-byte aligned offsets keep `arm64_alignment` meaningful on the concatenated sample (every
  slice starts at a block offset ≡ 0 mod 4 and is a multiple of 4 long, so the word alignment
  found on the sample is the block's alignment). For x86 the converter state is reset per block
  anyway (spec §4.2). On the ELF corpus the x86 filter decision on the 8×8 KiB sample agreed with
  the full trial on all 13 code-looking blocks [measured]; the one block where the full trial
  rejects the filter would cost +3,344 B (+0.02 pt) if forced.
* The 1/14 disagreement that remains at 1 MiB (corpus_versions block 1, 1,008,721 B: full trial
  xz 132,572 vs PPMd 140,723, every sample prefers PPMd by 12 %) is structural: the block holds
  versions of the same document and xz's long-range matches beat PPMd's order-16 model only over
  the whole block. Effort 4 (§2.3) is the answer, not a bigger sample.

### 2.2 Decision rule (new `compress_best` flow for efforts 2–4)

```text
compress_best(data, o):
  if o.effort == 5 or o.choice != Best or data.len() <= 2*n*SLICE:  -> today's code, unchanged
  if o.effort == 1:                                                  -> today's code with choice = Zstd
  s = sample(data)                                                   // §2.1, deterministic
  filters = [NONE] + x86 / arm64 candidates detected on s            // same heuristics, applied to s
  candidates = []
  for f in filters:
      in_s = apply_filter(f, s)
      z = zstd(in_s); incompressible = z.len()*100 >= in_s.len()*97
      push (f, ZSTD, z.len())
      if o.dict: push (f, ZSTD_DICT, ...)
      if incompressible: continue                                    // today's shortcut, on the sample
      if o.effort >= 2: push (f, XZ, xz(in_s).len())
      if o.effort >= 3 and looks_like_text(in_s): push (f, PPMD, ppmd(in_s).len())
  winner = first candidate with the minimal size, in push order      // == today's consider() tie-break
  run = [winner]
  if o.effort == 4 and winner.codec == PPMD: run.push((winner.f, XZ))  // xz safety net (§2.3)
  encode each (f, codec) in `run` on the whole block (PPMd params from ppmd_params(block len), as today);
  keep the smallest; store when nothing is smaller than data.len()
```

Properties: no codec id, parameter or filter that today's writer could not have produced; the
"store if nothing is smaller" and the 97 % rule keep their meaning; `looks_like_text` moves from
"first 64 KiB of the block" to "the sample" for efforts 2–4 only (a strided sample represents a
mixed block better; in the experiment this is what `trio(sample)` did).

**Measured outcome of this rule at 1 MiB (S8x8, winner-only = effort 3)** [measured/derived from
`blocks.jsonl`; codec seconds, single thread, summed over the blocks]:

| corpus | full trial (today) | effort 3 | loss vs full | vs zstd only | time vs zstd -19 | time vs today |
|---|---:|---:|---:|---:|---:|---:|
| corpus | 60.95 % | 60.95 % | +0.00 pt | −9.22 pt | 1.21× | 0.42× |
| corpus_versions | 48.24 % | 48.62 % | +0.37 pt | −6.55 pt | 0.96× | 0.32× |
| corpus_elf | 30.83 % | 30.83 % | +0.00 pt | −2.46 pt | 1.41× | 0.62× |

(Percentages here are blob bytes / input; the archive adds ≈ 1.2 pt of index/manifest.) Projected
whole-`pack` CPU including the floor [derived]: corpus ≈ 1.1 s vs 1.07 s zstd (1.0×) vs 2.27 s
today; corpus_elf ≈ 10.0 s vs 7.2 s zstd (1.4×) vs 15.9 s today. **Both roadmap targets (≤ 2×
zstd, ≤ 0.5 pt) are met on all three corpora with margin.**

### 2.3 `--effort 1..5` semantics

| effort | what runs per block (> 128 KiB) | ratio vs today [measured/derived] | codec time vs zstd -19 |
|---|---|---|---|
| 1 | zstd -19 only (identical to `--codec zstd`); filters still tried on code | +9.2 / +6.9 / +2.5 pt | 1.0× |
| 2 | sample decides between zstd and xz; **never PPMd** (LZ-only: fast, asymmetric decode) | +1.16 / +1.18 / +0.00 pt | 1.64× / 1.66× / 1.41× |
| 3 | sample decides among zstd, xz, PPMd(text); winner only | +0.00 / +0.37 / +0.00 pt | 1.21× / 0.96× / 1.41× |
| 4 | as 3, plus xz on the full block whenever PPMd won the sample (guards the one structural miss) | +0.00 / +0.00 / +0.00 pt | 1.83× / 1.93× / 1.41× |
| 5 | today's full trial, byte-for-byte the same code path | 0 | 2.9× / 3.0× / 2.3× |

Effort 2's time looks worse than 3's on text because xz then wins blocks that PPMd would have
taken more cheaply; its point is decode speed (PPMd is symmetric), not encode speed. A "runner-up
within m %" rule for effort 4 was also evaluated [derived]: m = 10 % fixes nothing here, m = 15 %
fixes the miss at 2.12× / 1.50× / 2.42× — the PPMd→xz safety net is cheaper and targeted, hence
the proposal.

Interaction with other options: `--effort` applies to `--codec best` only; `--codec zstd|xz|ppmd`
ignore it (documented; `--effort 1` with `best` is `zstd`). `--level` keeps its meaning for every
rung. Granular mode (`block_size = 0`): chunks ≤ 256 KiB, most ≤ 128 KiB → full trial as today;
larger chunks are sampled with zstd+dict as one more candidate. Delta (pack.rs:726–731) is
unchanged at every effort.

**Default in this PR: `effort = 5`** (see §2.5). Recommended later default: 3.

### 2.4 Determinism

* The sample is a pure function of the block bytes and its length (offsets computed from `len`,
  no RNG, no clock, no thread id); every codec call is the same deterministic library call the
  writer already makes; the decision is a pure function of the sample outputs and `CodecOptions`.
  Same input + same options (`effort` included) ⇒ same `Encoded` ⇒ same bytes.
* `flush_ready`'s `par_iter` maps blocks independently and writes in order (pack.rs:735), so
  `--jobs` cannot change the decision (covered by the extended `parallel_packing_is_deterministic`).
* `effort` is an option, not archive content: nothing is added to the manifest (a new manifest key
  would be a spec registration per CONTRIBUTING #5) — same policy as `--level` and `--jobs`.
* The tie-break order of the sampled decision is exactly `consider()`'s (first strictly smaller
  wins in push order), so where a sample equals the block the decision is today's decision.

### 2.5 Golden archives and the format freeze — recommendation

Facts [measured]: every golden archive is **one blob**: `full-default.tsr` 101,675 B,
`lite-default.tsr` 106,865 B, `canonical.tsr` 112,976 B, `base.tsr` 63,497 B, `incremental.tsr`
43,368 B (all `zstd`; `incremental` is `zstd+delta`). With the threshold of §2.1 (full trial at
≤ 128 KiB) **none of them would ever be sampled**, so efforts 2–5 all reproduce them by construction
(margin: 112,976 vs 131,072 B — thin but a property of the committed inputs, and a test can pin it).

Rules that apply: `docs/V1-CONTRACT.md` §2 ("the v1 writer must reproduce them byte for byte from
the same inputs and options; changing those bytes means changing the format"), P2 ("same inputs,
options *and build* produce the same bytes"), `CONTRIBUTING.md` §"Format freeze" (a change that
alters the golden bytes is a format event: new `tsaur_core::WRITER`, `make_golden.py`, CHANGELOG,
compatibility tests) and `lib.rs:43–46` (`WRITER = "tsaur-core/1.0"` exists "so that the same inputs
give the same bytes across patch releases").

Recommendation — **two steps**:

1. **This PR (1.1 cycle, no format event): `--effort` is opt-in, default 5.** `PackOptions::default()`
   and `CodecOptions::default()` carry `effort: 5`; the effort-5 branch is today's code, untouched.
   Default output is byte-identical for *every* input, not only the goldens; `tests/golden.rs`
   passes unchanged; `WRITER` stays `tsaur-core/1.0`; no spec id changes. This is the safe reading
   of "everything that needs no format change" in the roadmap and it lets the maintainer measure
   the ladder on real machines (the two-device plan) before committing to a default.
2. **A separate, deliberately labelled PR flips the default to 3.** Even though the golden bytes
   would not change (small blocks), output for larger inputs changes between releases, which is
   what `WRITER` is meant to signal; do it as a writer-generation bump: `WRITER = "tsaur-core/1.1"`
   → the `generator` string changes the golden bytes → regenerate with `tests/golden/make_golden.py`
   (both builds), refresh `MANIFEST.sha256`, CHANGELOG entry, `tools/compat_check.py`, spec §4.2
   prose at `TSAUR-FORMAT-SPEC-v1.0.md:107` ("`--codec best` tries … keeps the smallest" → "decides
   on a sample at effort < 5"), README/GUIDE tables. Codec ids, filter ids and reader behaviour do
   not change, so v1 readers are unaffected; the maintainer decides whether that counts as the
   "one v2 bump" bucket or an accepted 1.x golden regeneration. Do not fold this into step 1.

An alternative that avoids both a new default and a new flag — `--codec auto` as a new name for
the sampled mode — is not recommended: it duplicates `best` and the roadmap explicitly asks for
the effort dial.

## 4. Risks

1. **Structural misprediction (PPMd vs xz on version-heavy blocks)** — a sample cannot see
   redundancy that spans the block; measured cost +0.37 pt on `corpus_versions` at 1 MiB and
   +4.33 pt on the single 3.6 MiB `--solid 4` text block with a 4-slice sample (0.00 with 8+
   slices). Mitigations: ≥ 8 slices, slices scale with block size, effort 4's xz safety net.
   The `--solid` numbers rest on one block: verify in the PR.
2. **Prefix sampling would silently lose 6–9 points** on text corpora; the design, the tests
   (test 4) and the benchmark rows guard against someone "simplifying" the sampler later.
3. **Filter decided on a sample** (x86/ARM64): agreed on 13/13 code blocks with 8×8 KiB; worst
   observed penalty if wrong +0.02 pt; ARM64 needs the 4-byte alignment of slice offsets (test 6).
   Not measured on real ARM64 (`corpus_arm64` absent here).
4. **Substitute corpus**: `corpus_elf` is Linux x86-64 `.so`/binaries from this container, not the
   Windows DLL set of `corpus_binary` (30.9 % vs the README's 32.5 %); the qualitative result (xz
   always wins on machine code, the sample always agrees) is expected to transfer but is unverified.
5. **Timing environment**: 4 vCPUs with ≈ 2.6× aggregate scaling; xz/zstd at level 19 are
   memory-bound, so wall ratios on the maintainer's machines will differ; CPU ratios should not.
6. **Golden identity at efforts 2–4 is a property of small inputs** (max 112,976 B vs 131,072 B
   threshold). Regenerated or larger golden inputs would break test 9 without breaking the design;
   the test's message must say so. The default stays 5, so this is documentation, not a guarantee.
7. **Changing the default later is a writer-generation event** (§2.5): the `generator` string
   changes every golden; plan it as its own PR with `make_golden.py` from both builds.
8. **Small-block and granular archives gain nothing** (blocks ≤ 128 KiB run the full trial;
   `--block-kib 256` blocks are sampled with 25 % of their bytes) — document that the dial helps
   from ≈ 256 KiB blocks upwards; measured only at 1 MiB and 3.6–4.2 MiB.
9. **The delta trial is a separate time sink** (pack.rs:726–731: an extra zstd -19 with prefix on
   every block with a delta candidate; ≈ +0.7 s CPU on `corpus_versions` at `--codec zstd`); the
   effort dial does not reduce it. A later follow-up can decide the delta trial on the same sample
   [estimate: would bring `corpus_versions` effort 3 below 1× zstd]; do not mix it into this PR.
10. **Memory/allocation of the sample trials**: each PPMd sample allocates the 16 MiB minimum model
    (`ppmd_params`), and xz allocates its encoder per call; measured sample trials cost 0.01–0.05 s
    per block including that, i.e. ≤ 5 % of a 1 MiB block's winner run, but on many-core machines
    with `--jobs` = threads it is `threads × 16 MiB` transient extra. Reusing a PPMd model of 16 MiB
    for samples is an optional refinement.
11. **Behavioural surface**: `looks_like_text` on the sample instead of the first 64 KiB changes
    which blocks get a PPMd candidate at efforts 2–4 (never at 5); this is intended but must be in
    the doc comment so nobody "fixes" the discrepancy back.
12. **Library versions**: as today, upgrading `zstd`, `liblzma` or `ppmd-rust` changes bytes at every
    effort; the sampled path adds no new dependency and no new place where that can happen.
